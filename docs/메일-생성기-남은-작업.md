## 끝난 것

### 1. 템플릿 슬롯 가변화 (`4c2a0bb`, 베이스 브랜치)

슬롯 1~5 고정을 풀고 추가·이름변경·삭제가 가능해졌다.

핵심 결정은 슬롯 목록의 기준을 상수에서 **"행이 존재하면 템플릿이 존재한다"**로 옮긴 것이다.
상수와 DB를 합집합으로 두면 삭제한 슬롯이 새로고침에 되살아난다. 대신 빈 템플릿도 이름을
가지려면 행이 필요해서, 첫 진입 시 1~5를 시드로 만든다.

주의할 점 두 가지.

- `upsertSlot`은 `name`을 명시할 때만 이름 컬럼을 건드린다. 그렇지 않으면 300ms 자동 저장이
  매번 이름을 빈 문자열로 덮어쓴다.
- 빈 슬롯으로 전환할 때 베이스 템플릿을 채우는 판단은 행 존재가 아니라 **내용**(`isEmptySlot`)
  기준이다. 시드 행이 생긴 뒤에도 새 템플릿이 베이스 내용으로 열려야 한다.

### 2. 생성기 정의(JSON) 계약 (`c613e65`, `dc07930`)

생성기를 코드가 아니라 데이터로 추가하기 위한 스키마와 컴파일러.

- `lib/mail/generators/definition.ts` — zod 스키마. 이 파일이 계약 원본이다.
- `lib/mail/generators/compile.ts` — 정의 JSON을 기존 `GeneratorConfig`로 변환.
- `lib/mail/generators/seed.ts` — 기존 3종을 정의로 표현한 것.
- `lib/mail/generators/__tests__/verbatim.test.ts` — 이관 전후 동등성 검증.

설계 원칙은 세 가지다.

1. **필드 하나 = 플레이스홀더 하나.** 필드의 `name`이 곧 `{{...}}` 이름이고, 폼 표시명이
   다르면 `label`로 따로 준다(예: "도달"로 입력받아 `{{도달수}}`로 치환).
2. **계산식은 없다.** 기존 `computeValues`가 하던 일은 영문 state 키를 한글 플레이스홀더로
   옮기는 것과 날짜 표기를 바꾸는 것뿐이라, `date.format` 선택으로 전부 표현된다.
3. **한 필드가 여러 표기를 내야 하면 `also`에 이름을 명시한다.** 암묵 규칙을 두지 않는다.

`verbatim.test.ts`가 3종 모두에 대해 기본 제목·본문의 문자 단위 일치, 같은 입력에서의
`computeValues` 키·값 전체 일치, 렌더 결과 일치를 검증한다. **이 테스트는 반드시 통과시켜야
한다.** 기본 문구를 원본 그대로 유지하는 것이 PRD 전제였다.

이관하면서 확인한 사실도 적어 둔다.

- 안 쓰이는 플레이스홀더(`모집마감일전체`·`마감요일`·`디데이`·`직무명`·`활동분야`)는
  템플릿에서 사용 0회지만 **전부 보존한다.** 나중에 본문을 고칠 때 필요하다.
- 미선택 select 처리가 원래 서로 달랐다. sales만 빈 문자열, intern·activity는 첫 옵션.
  첫 옵션으로 통일했고, 폼이 항상 첫 옵션으로 시작하므로 실사용 결과는 같다.
- `josa`·`rawHtml`은 필드가 아니라 **출력 단위** 속성이다. 조사 처리는 "그 플레이스홀더가
  본문에서 조사와 붙는지"의 문제라 기본 출력과 부가 출력이 다를 수 있다.

### 3. 임시보관함 저장 기록 (`f23d223`)

Gmail 초안이 만들어질 때마다 한 줄 남기고 `/mail/log`에서 조회한다.

- `supabase/migration_mail_draft_logs.sql` — `mail_draft_logs` 테이블
- `lib/mail/draftLog.ts` — 기록·조회·필터(순수 함수)
- `app/mail/log/page.tsx` — 필터 화면
- `components/mail/GmailPanel.tsx` — 초안 저장 성공 직후 기록

필터는 생성기·템플릿·검색어(상대/받는사람/제목/템플릿)·기간을 지원한다. 행을 누르면 그때
입력했던 폼 값 전체를 펼쳐 본다.

설계상 짚어둘 점.

- **발송 기록이 아니라 저장 기록이다.** 이 앱은 메일을 보내지 않는다(`drafts.create`만).
- 슬롯이 지워져도 기록은 남아야 하므로 FK를 걸지 않고 그 시점의 템플릿 이름을 함께 박는다.
- `delete` 정책을 두지 않아 기록 삭제를 막는다.
- 로그 기록 실패가 초안 저장을 되돌리지 않는다. 초안은 이미 만들어진 뒤다.
- 날짜는 `localDateKey`로 로컬 기준으로 자른다. `toISOString`으로 자르면 한국 시간 오전 9시
  이전 기록이 전날로 밀린다.

어느 필드가 "상대 이름"인지는 `GeneratorConfig.counterpartyFieldId`가 지정한다. 코드 config
3종과 JSON 정의(`field.counterparty`) 양쪽에서 동일하게 동작하도록 심어 두었다.

## 남은 작업

### 1단계. 생성기 DB 전환 — 밑작업 완료, UI 미연결

`lib/mail/generators/store.ts`와 `supabase/migration_mail_generators.sql`은 만들어 두었으나
**아직 아무 데서도 import 하지 않는다.** 지금 `/mail`은 여전히 코드 config 3종을 쓴다.

`store.ts`가 제공하는 것:

- `loadGenerators` — 한 생성기의 JSON이 깨져도 나머지는 뜨도록 개별 검증 후 `broken`으로 분리
- `seedGeneratorsIfEmpty` — 테이블이 비었을 때만 3종 시드. 이미 있으면 건드리지 않는다
- `upsertGenerator` / `setGeneratorEnabled` — 저장, 감추기(삭제 아님)

해야 할 일:

1. `supabase/migration_mail_generators.sql` 실행
2. `app/mail/page.tsx`의 하드코딩 `TABS` 배열을 `loadGenerators` + `visibleGenerators`로 교체
3. `compileGenerator`로 얻은 config를 `MailGenerator`에 전달, 초기값은 `initialFieldValues`
4. 로드 실패·`broken`이 있을 때 화면에 경고 표시(조용히 사라지면 원인을 못 찾는다)

이 단계까지 하면 동작은 그대로인 채 데이터 기반으로 바뀐다. 여기서 한 번 검증할 것.

### 2단계. 생성기 편집 화면

JSON을 붙여넣어 생성기를 추가·수정하는 화면. 폼 빌더 UI는 만들지 않는다 — 같은 JSON 스키마
위에 나중에 얹을 수 있고, 지금은 구현 비용이 훨씬 크다.

필요한 것:

- 텍스트 영역 + 저장. 저장 전 `parseGeneratorDefinition`으로 검증하고 **실패하면 저장을 막고
  어디가 틀렸는지 보여준다.** 이게 없으면 잘못된 JSON이 들어가 생성기가 조용히 깨진다.
- 기존 생성기 정의를 불러와 편집
- 순서 변경(`sort_order`), 감추기(`enabled`)
- 새 생성기는 시드 하나를 복제해 시작하는 편이 백지보다 쓰기 쉽다

### 3단계. 코드 config 정리

1·2단계가 끝나고 DB 정의가 원본이 되면, `lib/mail/configs/{sales,intern,activity}.ts`의
config 객체는 역할이 끝난다. 다만 **기본 제목·본문 문구와 select 옵션의 원본이 아직 이 파일들**
이고 `seed.ts`가 참조하고 있다.

정리 순서:

1. 시드가 DB에 들어간 것을 확인
2. 문구·옵션을 `seed.ts`로 옮기거나, 시드 전용으로 남길지 결정
3. `verbatim.test.ts`는 비교 대상이 사라지므로 "현재 정의가 기대 문구와 같은지" 형태로 전환

이 단계는 급하지 않다. 두 벌이 공존하는 동안 `verbatim.test.ts`가 어긋남을 잡아 준다.

## 알아둘 것

- **dev 서버를 켜 둔 채 `next build`를 돌리지 말 것.** 둘 다 같은 `.next`를 써서 dev 서버가
  참조하던 청크가 날아간다(`Cannot find module './331.js'`). 빌드 전에 dev를 내린다.
- **`.env`의 `APP_PASSWORD`를 바꾸면 dev 서버를 재시작해야 한다.** API 라우트(Node)와
  미들웨어(Edge)가 env를 따로 들고 있어서, `Reload env`만으로는 미들웨어가 옛 값을 유지한다.
  증상은 "로그인은 200인데 계속 `/login`으로 튕김"이다.
- **ESLint는 이 프로젝트에 설정되어 있지 않다.** `npm run lint`는 초기 설정을 물어본다.
  검증은 `npx tsc --noEmit`와 `npx vitest run`으로 한다.
- 현재 테스트 214개. 브랜치를 정리하기 전에 전부 통과하는지 확인할 것.
